# EasyPatch agent for Linux

The Linux agent is a systemd service (`easypatch-agent`) that reports the package upgrades
available from the distribution's package manager (apt on Debian and Ubuntu, dnf on Red Hat
Enterprise Linux and its rebuilds) and installs the upgrades an administrator approves. It uses
the same server, enrollment, policies, jobs and console as the Windows agent
([agent-installation.md](agent-installation.md)). The agent:

* **restarts the computer only when an administrator asks for it**, once or through a restart
  schedule set in policy. Installing packages never restarts the computer. It reports when a
  restart is pending and why;
* **only upgrades packages that are already installed**, to the exact version it reported. It
  does not install new software, remove packages, change repositories or upgrade the
  distribution release;
* **does not change the package manager configuration**. `unattended-upgrades` and
  `dnf-automatic` are reported in the console, never enabled or disabled;
* cannot run commands. It executes four job types: update scan, inventory refresh, install
  updates and restart, plus agent updates (see [Updating the agent](#updating-the-agent)) and
  removing its own package (see [Uninstalling](#uninstalling)).
  There is no tray icon, so preset messages to signed-in users are Windows only. Removing an
  installed update and downloading updates before the maintenance window are Windows only too.

## Supported distributions

| Family | Distributions | Package manager | Tested by the project |
|---|---|---|---|
| Debian | Debian 11, 12, 13; Ubuntu 20.04, 22.04, 24.04, 26.04 LTS and interim releases | apt | Debian 12 and 13; Ubuntu 22.04, 24.04, 26.04 and 26.10 |
| Red Hat | Red Hat Enterprise Linux 8, 9, 10 and Rocky Linux, AlmaLinux, Oracle Linux 8 and later; CentOS Stream 9 and 10; Fedora | dnf (dnf4 and dnf5) | Rocky Linux 8 and 9, AlmaLinux 10.2, Fedora 45 |

The family is detected from `ID` and `ID_LIKE` in `/etc/os-release`. Debian and Ubuntu
derivatives that declare `ID_LIKE=debian` or `ubuntu` are treated as Debian; distributions that
declare `rhel`, `centos` or `fedora` are treated as Red Hat. Of these, only the releases in the
table are tested.

* **dnf4 and dnf5.** RHEL 8 to 10 and their rebuilds use dnf4; Fedora 41 and later use dnf5,
  whose output differs. The agent detects which one is installed (`dnf --version`) and reads
  dnf5's advisory list as JSON.
* **x86-64-v2 builds.** RHEL 10 and most rebuilds need an x86-64-v3 CPU. AlmaLinux also
  publishes an x86-64-v2 build for older CPUs; its packages have the architecture `x86_64_v2`,
  which the agent reports and installs like any other. (AlmaLinux 10.2 was tested with that
  build, because the project's test host has no x86-64-v3 CPU.)
* **CentOS Stream** publishes no security advisories, so its updates are never classified as
  security updates.

**Not supported:** RHEL/CentOS 7 and other systems without dnf (the agent needs glibc 2.27 or
later), SUSE (zypper), Arch, Alpine (musl), systems without systemd, and 32-bit systems.

### Requirements

| | |
|---|---|
| Architecture | x86_64 (`x64` packages) or aarch64 (`arm64` packages) |
| Init system | systemd |
| Privileges | Installation and the `enroll`, `scan` and `unenroll` commands need root. The service runs as root |
| Network | Outbound HTTPS from the endpoint to the EasyPatch server. No inbound ports. apt and dnf use their own repository configuration and proxy settings |
| TLS | The server certificate must be trusted by the system CA store (`/etc/ssl/certs` or `/etc/pki/tls`). Certificate validation cannot be disabled |
| .NET | Not required: the agent is a self-contained executable |
| Reboot detection on Red Hat | `dnf needs-restarting` (package `dnf-plugins-core` or `dnf-utils`); without it only a newer installed kernel is detected |

## Installing

Both enrollment methods from the Windows agent are available: a **deployment code** (no secret,
each computer waits for approval) and an **enrollment token** (a secret, active immediately).
See [Choosing an enrollment method](agent-installation.md#choosing-an-enrollment-method).

### Deployment code: install script

*Deploy → Deployment codes → Linux* shows the one-line installer for a code:

```sh
curl -fsSL https://patch.example.com/downloads/install/EPD-XXXXXXXXXXXXXXXX.sh | sudo sh
```

The script is generated by the server for that code and contains no secrets. It:

1. checks that it runs as root on a supported distribution and architecture with systemd;
2. downloads the newest `.deb` or `.rpm` package for the computer from the server over HTTPS
   (curl or wget) and checks its SHA-256 against the value in the script;
3. writes `/etc/easypatch/agent.conf` (mode 0600) with the server URL and the deployment code,
   unless the agent is already enrolled or waiting for approval (`easypatch-agent status`). An
   agent that was installed earlier but never enrolled is restarted after the settings are
   written, so it enrolls immediately;
4. installs the package with `apt-get install` or `dnf install`, which enables and starts the
   service;
5. waits up to a minute for the agent to create its enrollment request and prints
   `easypatch-agent status`, including the key fingerprint.

The computer then appears under *Pending Approvals*. Compare the key
fingerprint with the one printed on the computer before approving. Running the script on a
computer that is already enrolled upgrades the package if needed and keeps the enrollment.

To have the agent reach the server through a proxy, set `EASYPATCH_PROXY_URL` for the script
(`sudo` does not pass the environment through, so set it after `sudo`):

```sh
curl -fsSL https://patch.example.com/downloads/install/EPD-XXXXXXXXXXXXXXXX.sh | sudo EASYPATCH_PROXY_URL=http://proxy.example.com:3128 sh
```

The proxy is used by the agent only. Proxy credentials are not supported.

### Enrollment token

1. Download the package for the computer from *Deploy → Agent packages* (or from
   `https://patch.example.com/downloads/agent/EasyPatchAgent-<version>-<arch>.<deb|rpm>`) and
   compare its SHA-256 with the one shown there.
2. Install it. The service starts and waits for enrollment.

   ```sh
   sudo apt-get install ./EasyPatchAgent-1.10.0-x64.deb     # Debian, Ubuntu
   sudo dnf install ./EasyPatchAgent-1.10.0-x64.rpm         # RHEL and rebuilds, CentOS Stream, Fedora
   ```

3. Enroll with the token. The agent does not accept a token as a command-line argument, because
   arguments are visible to every user in the process list. Read it from a root-only file, from
   standard input, or from the `EASYPATCH_ENROLLMENT_TOKEN` environment variable:

   ```sh
   sudo easypatch-agent enroll --server https://patch.example.com --token-file /root/easypatch-token
   ```

   When a token is created, the console shows a ready-made command that pipes the token in
   (`printf '%s' '<token>' | sudo easypatch-agent enroll … --token-file -`). `printf` is a shell
   builtin, so the token does not appear in the process list, but it can end up in your shell
   history. Use a token file in scripts.

`sudo easypatch-agent enroll --server <url> --deployment-code <code>` enrolls with a deployment
code without the install script.

## What the package installs

| Path | Contents |
|---|---|
| `/opt/easypatch/easypatch-agent` | The agent (single self-contained executable) |
| `/usr/sbin/easypatch-agent` | Symbolic link to the agent |
| `/usr/lib/systemd/system/easypatch-agent.service` | The service. Enabled and started on installation, restarted on upgrade |
| `/etc/needrestart/conf.d/easypatch-agent.conf` | Tells needrestart (Debian, Ubuntu) not to restart the agent while it installs packages |
| `/etc/easypatch/agent.conf` | Bootstrap settings: `ServerUrl`, `DeploymentCode` or `EnrollmentToken`, `ProxyUrl`, `LogLevel`. Root only (0600). Written by `enroll` or the install script, not by the package. The token and deployment code are removed from it after enrollment |
| `/var/lib/easypatch` | Root only (0700): agent identity and state, logs, package work files, downloaded agent updates |

The service runs with `UMask=0077`, `Restart=always` and `KillMode=mixed`, and reports
readiness to systemd (`Type=notify`). The agent refuses to start when it is not root, when the
distribution is not supported, or when another agent process holds `/var/lib/easypatch/agent.lock`.

## How it works

Check-in, scan and inventory schedules, policies, approvals, maintenance windows and job handling
are the same as on Windows ([architecture.md](architecture.md)). The Linux-specific parts:

**Scanning.** The agent refreshes the package lists (`apt-get update` or `dnf makecache`) and asks
the package manager which installed packages can be upgraded (`apt-get -s upgrade
--with-new-pkgs`, `dnf check-update`). Packages that are held (`apt-mark hold`, dnf versionlock)
are not offered. Each upgrade becomes one update in EasyPatch: one version of one package for
one distribution release, so the same upgrade on 50 Debian 12 servers is one row in the fleet
view.

**Classification.** An upgrade is a **Security** update when:

* apt: the new version is available from a `*-security` suite (Debian security, Ubuntu security,
  and Ubuntu Pro ESM security);
* dnf: a security advisory in the repository's `updateinfo` covers it. The advisory IDs (for
  example `RHSA-2024:1234`, `RLSA-…`, `ALSA-…`, `ELSA-…`, `FEDORA-2026-…`) and severity are
  shown.

Everything else is classified as **Other**. Policies select Linux updates by these categories,
like Windows updates.

**CVEs** (agent 1.4.0 and later). On dnf systems the agent also reads the CVE references of the
advisories that cover each upgrade, from the local metadata cache (`dnf updateinfo list --updates
--with-cve` on dnf 4, `dnf advisory info --updates --json` on dnf 5), and reports at most 200 per
upgrade. On Debian and Ubuntu it reports each package's source package (`dpkg-query`), which the
server matches against the Debian Security Tracker. Ubuntu CVEs are not matched yet. If reading
the CVEs fails, the scan still succeeds without them. See
[compliance.md](compliance.md#vulnerabilities-and-known-exploited-updates).

**Installing.** An install job installs all of its approved packages in one apt or dnf
transaction, at the exact versions the agent reported. The transaction runs in a transient
systemd unit (`easypatch-packages`), so it is not interrupted if the agent restarts, and its
output is kept in `/var/lib/easypatch/packages/transaction.log`. On Debian and Ubuntu, apt
is told not to remove packages and to keep locally changed configuration files; on Red Hat,
rpm writes new configuration files as `.rpmnew`. If another process holds the dpkg lock, the
agent waits for up to 30 minutes. If dpkg was interrupted earlier, the agent runs
`dpkg --configure -a` once and tries again. When the transaction fails, the agent tries the
remaining packages one at a time. Upgrades of glibc or systemd make systemd re-execute itself
during the transaction; while systemd does not answer, the agent keeps waiting (for up to
5 minutes without an answer) instead of assuming that the transaction has ended.

An update is reported as installed only after the package database shows the new version.
The package manager may also upgrade or install dependencies of approved packages, and these
are reported as installed too. Packages that were installed as dependencies keep their
"automatically installed" mark.

**Restart detection.** A restart is reported as pending when `/run/reboot-required` exists
(Debian, Ubuntu), when `dnf needs-restarting -r` says so (Red Hat), or when a newer kernel of
the running flavour is installed. Kernel updates are shown as requiring a restart, and updates
to glibc, systemd, OpenSSL and similar packages as possibly requiring one.

**Restarting.** A restart job runs `shutdown -r +<minutes> "<message>"`, which broadcasts the
message to signed-in terminal users. Signed-in users are counted with `who` (local and SSH
sessions); as on Windows, the warning period applies only when someone is signed in. Cancelling
the job before the restart runs `shutdown -c`.

**Update history.** Linux has no equivalent of the Windows Update history, so the *History* tab
stays empty. The agent remembers the upgrades it reported for 30 days and reports them as
installed when the package database shows them installed, also when they were installed outside
EasyPatch.

**Inventory.** Distribution and version, kernel, package manager, hardware (DMI), memory, disk,
virtualization (`systemd-detect-virt`), the automatic-update tool and whether it is enabled,
and Ubuntu Pro ESM. The operating system support status uses the distribution's end-of-life
dates; for Ubuntu LTS releases past standard support, an enabled Ubuntu Pro ESM service counts as
extended security updates.

## Updating the agent

Linux agents update themselves exactly like Windows agents, controlled by the same *Agent updates*
policy (see [Automatic and console updates](agent-installation.md#automatic-and-console-updates-agent-120-and-later)).
An agent is offered only packages in its own format (`.deb` or `.rpm`) and architecture, and is
never downgraded.

During an update the agent checks the release signature against the key built into it, checks
that the package is newer and in its format and architecture, downloads it, checks its size and
SHA-256 and installs it with `apt-get install` or `dnf --disablerepo='*' install` in the transient
unit `easypatch-agent-update`. The package's maintainer scripts restart the service; the new agent
reads the result of the unit and completes the job. The computer is not restarted. The package
and the installer output are kept in `/var/lib/easypatch/updates` (`install-<version>.log`).

To release a version, build it with `scripts/build-linux-packages.sh` (see
[Building from source](#building-from-source)) and copy the `.deb` and `.rpm` packages with their
`.sig` files to `data/agent-packages` on the server.

## Credential protection

The agent's private key is encrypted with `systemd-creds` and the host key
(`/var/lib/systemd/credential.secret`) when systemd 250 or later is available (Debian 12 and later,
Ubuntu 24.04, RHEL 9 and later). Otherwise (Ubuntu 22.04, RHEL 8) it is protected by file permissions
only (root only, mode 0600). The console shows which one each endpoint uses. Root can read the key
in both cases; the host key means that a copy of `/var/lib/easypatch`, for example in a backup, is
useless without the host key file. A TPM is not used.

## Command line

```text
Usage: easypatch-agent <command> [options]

  run                       Run the agent (default; used by the easypatch-agent systemd service).
  enroll --server <url> (--token-file <path|-> | --deployment-code <code>) [--proxy <url>] [--force] [--no-start]
                            Enroll this computer. A token enrolls immediately; a deployment code
                            creates a request an administrator must approve in the console.
                            The token is read from a file, from standard input (--token-file -)
                            or from EASYPATCH_ENROLLMENT_TOKEN; it is never accepted as an argument.
  status [--json]           Show enrollment and agent status.
  scan [--json]             List the package updates this computer would report (refreshes the package
                            lists; installs nothing and does not contact the server).
  unenroll [--reason <text>]
                            Notify the server (best effort) and delete the agent identity.
  version                   Print the agent version.

Exit codes: 0 success, 1 failure, 2 usage, 3 enrolled with another server (use --force),
            4 rejected, 5 not root, 6 server unreachable (saved; the service retries), 7 busy.
```

## Logs

* `journalctl -u easypatch-agent`: information, warnings and errors.
* `/var/lib/easypatch/logs/agent.log`: the agent log (10 MB per file, 10 files). Set
  `LogLevel=Debug` in `/etc/easypatch/agent.conf` and restart the service for more detail.
* `/var/lib/easypatch/packages/transaction.log`: output of the last package installation.
* `systemctl status easypatch-packages easypatch-agent-update`: the last package installation
  and agent update units.

Package manager output sent to the server has credentials in repository URLs removed.

## Uninstalling

From the console (agent 1.6.0 or later): open the endpoint, **More → Uninstall agent…** and type
the computer name to confirm. The agent removes its own package (`apt-get remove
easypatch-agent` or `rpm -e easypatch-agent`, in the transient unit
`easypatch-agent-uninstall`) the next time it checks in. The job completes when the package's
removal script has unenrolled the agent, and the endpoint is shown as decommissioned. The
output is in `/var/lib/easypatch/logs/uninstall.log`.

On the computer:

```sh
sudo apt-get remove easypatch-agent      # keeps /etc/easypatch and /var/lib/easypatch
sudo apt-get purge easypatch-agent       # also deletes them
sudo dnf remove easypatch-agent          # keeps them; delete them by hand:
sudo rm -rf /etc/easypatch /var/lib/easypatch
```

Since 1.6.0, removing the package (not upgrading it) stops the service and runs `unenroll`
first, so the server marks the endpoint as decommissioned when it can be reached. With older
packages, run `sudo easypatch-agent unenroll` before removing them, or remove the endpoint in
the console.

## Troubleshooting

| Symptom | What to check |
|---|---|
| `The agent is not enrolled and has no server URL` in the journal | The package was installed without enrolling. Run `sudo easypatch-agent enroll` or the install script |
| The endpoint does not appear under *Pending Approvals* | `easypatch-agent status`, `journalctl -u easypatch-agent`; that the computer can reach the server (`curl -I https://patch.example.com/health/live`) and trusts its certificate |
| Updates shown in the console differ from what you expect | `sudo easypatch-agent scan` shows what the agent reports, without contacting the server |
| An install job fails with `apt_failed` or `dnf_failed` | The job's error message and `/var/lib/easypatch/packages/transaction.log` |
| A restart is never reported as pending on Red Hat | Install `dnf-plugins-core` (`dnf needs-restarting`) |
| An agent update fails | `/var/lib/easypatch/updates/install-<version>.log` and `systemctl status easypatch-agent-update` |

## Building from source

The `.deb` and `.rpm` packages attached to
[GitHub Releases](https://github.com/paulmataruso/EasyPatch/releases) are built and signed by the
project's `release` workflow; most installations should use those (see
[installation.md](installation.md#6-offer-agent-packages)). An agent you build with your own
release key accepts only packages signed with that key, so it does not update to official
releases (see [security.md](security.md#agent-release-signing)).

```sh
scripts/build-linux-packages.sh --version 1.10.0 --arch all
```

The script runs the agent tests, publishes the self-contained agent for linux-x64 and linux-arm64,
builds the `.deb` and `.rpm` packages in a pinned container image without network access, checks
the files in each package against the published files, writes `.sha256` files and signs each
package with the release key (`~/.easypatch/easypatch-release-key.pem`, see
[Building from source](agent-installation.md#building-from-source)). The output is in
`artifacts/linux`. It needs the .NET 10 SDK and Docker.
