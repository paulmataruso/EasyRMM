# W3 (the Windows hardening console), notes for the integrator

Branch `ws/w3`, migration `90271_hardening_guard_keep.sql` (renumber; adds
`hardening_guards.keep_requested_at`).

## Changelog lines

* Windows computers have a Hardening tab: each module's risk tier and state,
  each setting's value, owner and rules, apply and undo by module or setting
  with the tier's confirmation (typed name and step-up for tier 3), the
  guard's countdown with a Keep button, and the history (ADR-0054, W3).
* Organizations, sites and groups have a Hardening tab with the Windows
  computers and each module's states summed.
* New endpoints: `GET /hardening/windows/catalog`, `GET /hardening/windows/fleet`,
  `GET /devices/{id}/hardening/guards`, `POST /devices/{id}/hardening/guard/keep`.
* The Devices list's "not checked" hardening filter covers Windows computers.

## Implementation-status rows

* ADR-0054 W3: partly built. Per-module and per-setting views, apply and undo
  with confirmation, guard with Keep, history, fleet at organization, site and
  group. Not built: mixed selections as one job per platform, harvest coverage
  and two-step state. Not run on a real Windows computer.

## Privacy

Nothing new leaves a computer. Keep writes one audit row
(`device.hardening.guard_keep`) with the job id and setting IDs.

## For the integrator

* Hotspot edits (additive): `DeviceDetailPage.tsx` (the Hardening tab shows for
  Windows and picks `WindowsHardeningPanel`), `levelTabs.tsx` (one line),
  `GroupDetailPage.tsx` (a tab), `jobsapi.go` (four routes),
  `devices.go` (`canHarden` and the `unchecked` filter include Windows).
* `windows_hardening_guard.go`: the confirm-job insert moved into
  `insertConfirmJob`, which Keep reuses.
* The check dialog for Windows runs every module; a chooser is not built.
* Org scope (`devscope`): Keep is an operator's own action, so it is not
  gated; the automatic guard queueing still is.
* The Linux hardening console (`DeviceHardening.tsx`) is untouched.
