# ADR-0005: MeshCentral users, groups, login tokens and session launch

* Status: Accepted (2026-11-15)

## Context
A MeshCentral login token carries the full rights of the MeshCentral user it
names. Using one shared administrator for all embedding would let any
technician reach any device through MeshCentral's own UI or WebSocket.

## Decision
* One MeshCentral **device group per EasyRMM site**, created and renamed by
  our server.
* One MeshCentral **user per EasyRMM user** that holds any remote permission,
  named `easyrmm-<user-uuid>`, random password never shown, real name set to
  the user's display name (shown in end-user consent prompts).
* Rights are derived from EasyRMM RBAC and pushed with `addmeshuser` per
  group (desktop, terminal and files bits only as permitted); revocation
  removes them. Changes are event-driven with a periodic reconciliation.
* A single persistent `control.ashx` connection, as a dedicated service
  administrator, correlates requests by `responseid` and reconnects with
  backoff.
* Login tokens use the AES-256-GCM format only, with `expire:1` and a random
  `once` value. The `loginCookieEncryptionKey` is generated by our server,
  sealed at rest, and written to MeshCentral's config.
* Every launch is authorized by our server for the specific device and
  permission and audited before a token is issued.

## Consequences
* We depend on MeshCentral's `control.ashx` protocol, which is unversioned;
  integration tests pin the MeshCentral version and run against the real
  container.
* Per-device restrictions finer than a site use `adddeviceuser`.
